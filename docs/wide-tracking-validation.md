# 고정 파노라마 추적 대조

SoccerTrack v1 동일 경기의 0~30초의 소수 프레임으로 만든 실험 후보와 일반 YOLO11n을 다른 시간대인 60~90초의 연속 프레임에 적용했다. 둘 다 원본 6500×1000을 타일로 나누고 ByteTrack을 쓰며 confidence는 0.35다. 정답으로 팀 0/1의 ID 0을 제외한 선수 박스를 사용했고, 서로 다른 정답과 탐지를 IoU 0.5 이상 기준으로 탐욕적으로 일대일 매칭했다. 누락된 주석·심판 탐지는 미매칭에 포함되므로 오탐으로 단정하지 않는다. 정답 상자를 프레임 100에 겹쳐 대체로 선수와 정렬되는지 확인했으나 주석 자체 오차 가능성이 있다.

서로 다른 두 시간 구간에서 얻은 결과(반복 프레임은 독립 표본이 아님):

| 영상 인덱스 | 모델 | 정답 | 예측 | 매칭 | 정답 기준 매칭 비율 | 예측 기준 매칭 비율 | 연속 프레임 ID 변화 |
|---|---|---:|---:|---:|---:|---:|---:|
| 100~199 | 기본 | 2200 | 1292 | 579 | 26.3% | 44.8% | 1 |
| 100~199 | 광각 후보 | 2200 | 1524 | 1297 | 59.0% | 85.1% | 3 |
| 350~449 | 기본 | 2200 | 1954 | 1028 | 46.7% | 52.6% | 4 |
| 350~449 | 광각 후보 | 2200 | 1529 | 1187 | 54.0% | 77.6% | 3 |

같은 350~449 프레임에서 원본 6500px 전체를 640px로 한 번에 처리한 기본 모델은 추적 상자가 0개였고 17.39fps였다. 타일 분할 기본 모델은 위처럼 1028개를 매칭했지만 6.62fps였다. 속도는 서로 다른 시점에서 다른 GPU 작업과 경쟁한 수치다.

ID 변화는 **바로 이전 프레임과 이번 프레임 양쪽에서 같은 정답 ID가 매칭됐으나 추적 ID가 바뀐 횟수**다. 가려진 후 재출현의 ID 교체는 빠지므로 IDF1·HOTA·표준 MOT 집계가 아니다. 두 구간 모두 같은 경기·카메라이므로 독립 경기 일반화는 평가하지 못한다. 100~199에서 후보 confidence를 0.20으로 낮추면 정답 기준 매칭은 66.6%였지만 연속 ID 변화가 13회로 늘었다. 현재는 0.35를 유지하는 편이 낫다.

350~449 측정은 다른 프로세스도 GPU를 쓰는 상황에서 기본 6.62fps, 후보 6.54fps였다. PyTorch 최대 할당 메모리는 각각 83.3/77.4MiB, 예약 메모리는 각각 110MiB였고 CUDA 컨텍스트 및 다른 프로세스를 포함한 전체 VRAM이 아니다. 시간·GPU 부하가 같지 않아 엄밀한 속도 비교는 아니다.

기존 평가에서는 광각 후보가 다른 AI Hub 경기에서 성능이 크게 저하됐다. 따라서 **해당 경기 재생 전용 실험 가중치**로만 제한해 시험하고, 다른 경기나 아이폰 스트림의 기본 모델을 교체하지 않는다. 팀·역할·경기장 좌표·전술 코칭 정확도는 이 실험의 평가 대상이 아니다.

로컬 승인 데이터와 가중치가 있는 환경에서 `python scripts/evaluate_wide_tracking.py --video <mp4> --labels <csv> --weights <pt> --mode tiled --device cuda:0 --start 350 --frames 100`으로 재현한다. 원본 영상, 주석, 실험 가중치는 저장소에 포함하지 않는다.
