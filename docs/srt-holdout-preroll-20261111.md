# 동기화 SRT 평가: 준비구간과 남은 오류

2026-11-11에 SoccerTrack v1 `match-20200220/0060_0090`의 350~599번 프레임을 로컬 루프백 SRT→MediaMTX→RTSP로 보냈다. 원본을 18비트 프레임 마커가 있는 MJPEG로 만든 다음 H.264로 다시 인코딩했다. 이 경기의 정답은 두 모델의 학습에 넣지 않고 채점에만 사용했다. 원본 사전 학습 가중치의 전체 학습 이력은 확인하지 못했다. 이 영상은 기존 프로젝트 실험에도 사용했으므로 독립적인 최종 시험은 아니다.

모델 로드 전에 전송을 시작했던 이전 측정에서는 처음 채점한 프레임이 465/466이었다. 첫 영상 프레임을 8초간 반복하고 마지막 프레임을 2초간 반복하자 두 모델 모두 350부터 채점했다. 이 결과는 수신기 준비 중 초기 영상이 지나갔다는 가설을 지지하지만 정확한 시간별 원인을 따로 계측한 것은 아니다. 반복 마커는 한 번만 채점하며 중복 횟수는 네트워크 손실 수치가 아니다.

프로세스에서만 `OPENCV_FFMPEG_CAPTURE_OPTIONS=rtsp_transport;tcp`를 지정한 시험에서는 두 모델이 각각 45개와 42개의 서로 다른 프레임을 채점했고 마지막 599번 프레임에도 도달했다. 두 실행에서 동일하게 채점한 프레임은 15개, 정답 상자는 330개였다. IoU 0.5 이상 일치는 원본 YOLO11n(신뢰도 0.35) 102/330, 102/166 예측, 9개 다른 AI Hub 경기로 추가 학습한 모델(신뢰도 0.95) 121/330, 121/248 예측이었다. 정답 노출 뒤 탐지 공백이 있었다가 다시 매칭된 경우 기존 ID 유지/변경은 각각 3/18과 7/19였다. 표본이 적고 시간상 서로 상관되며 임계값도 다르므로 일반적인 성능이나 IDF1이 아니다. GT에 포함되지 않은 선수나 가려진 선수의 실제 위치는 평가하지 못한다.

TCP 지정 이후에도 H.264 매크로블록 오류가 계속 나왔다. 전송 종료 시 분석기는 `Stream disconnected`를 기록했고 당시 송신 프로세스가 살아 있었으므로 단순한 정상 종료라고 단정할 수 없다. TCP 지정 전후 각 1회에서 관측 프레임 수가 달랐지만 확률적 부하와 모델 초기화 시간이 통제되지 않아 개선의 원인을 전송 방식으로 돌릴 수 없다. 특히 6500×1000 초광폭 비디오, 실시간 인코딩, SRT 및 RTSP, 디코더 가운데 손상 발생 지점을 별도로 계측해야 한다. 실시간 프레임 드롭은 최신 프레임 처리 설계와도 섞여 있다. 실제 아이폰 또는 외부 네트워크의 안정성은 시험하지 않았다.

## 재현

기존 `scripts/evaluate_labeled_srt.py`에 `--preroll-seconds 8 --tail-seconds 2`를 전달한다. 두 값의 기본값은 0초이며 0~30초로 제한된다. 입력 영상, 레이블, FFmpeg, MediaMTX 및 가중치 경로를 명시하고 `--start 350 --frames 250 --output <별도 JSON>`을 지정한다. 두 모델에는 각각 `--confidence 0.35`와 `--confidence 0.95`를 사용했다. TCP 시험 시 실행할 PowerShell 프로세스에서만 `$env:OPENCV_FFMPEG_CAPTURE_OPTIONS='rtsp_transport;tcp'`를 설정한다. JSON은 영상별 선수 추적 매칭을 포함하므로 로컬에 보관한다. `scripts/compare_labeled_srt.py --first <첫 JSON> --second <둘째 JSON> --labels <정답 CSV>`로 공통 프레임만 비교한다. 사용자 운영 서버를 건드리지 않고 전용 포트 23974/23574를 사용하는 스크립트다.

다음에는 원본, MJPEG, H.264 파일을 각각 디코딩하고 SRT 구간과 RTSP 구간에서 같은 바이트 또는 프레임 검사를 수행해 최초 손상 지점을 분리한다. 안정적인 동기화와 별도 경기에서 충분한 공통 샘플을 확보하기 전에는 우열이나 전술 코칭 정확도를 확정하지 않는다.
