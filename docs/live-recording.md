# 원본 송출 녹화

## 실행 중인 녹화의 읽기 전용 점검

녹화 프로세스를 건드리지 않고 기존 세그먼트의 크기 변화와 저장 공간을 점검할 수 있다. 실제 실행 중인 MediaMTX의 작업 디렉터리와 설정에 따라 경로가 달라지므로, 사용 중인 녹화 폴더를 직접 지정한다.

```powershell
python -m app.recording_health --directory 'C:\path\to\recordings\match' --sample-seconds 5
```

파일 증가가 관측되지 않아도 송출 중단이나 녹화 완료를 뜻하지 않는다. 파일 분할 직전·버퍼링·네트워크 중단 등은 별도로 확인해야 한다. `low_space`는 기본 30 GiB 미만에 표시하며 서버의 상시 알림은 아니다. 서버를 재시작하거나 녹화 파일을 수정·삭제하지 않는다. 방송을 종료한 뒤 마지막 세그먼트 크기가 안정되는지 확인하고, `ffprobe`로 파일의 스트림과 길이를 검사한다. 검사 성공도 모든 프레임이나 재생 기기 호환성을 보장하지 않는다.

`app.secure_srt`, `app.secure_srt_lan`, `app.srt_path_ingest`로 새로 시작한 MediaMTX의 `match` 경로는 기본적으로 수신 스트림을 fMP4로 저장한다. 재인코딩은 설정하지 않았다. 10분 단위 세그먼트와 1초 part이며 스트림 재연결 등으로 더 짧은 파일이 생길 수 있다. 파일명에는 로컬 날짜·시간·마이크로초·시간대가 포함된다. 자동 삭제를 명시적으로 끈다(`recordDeleteAfter: 0s`). 운영체제나 전원이 갑자기 꺼지면 최근 part와 쓰기 중인 데이터가 손실될 수 있으며 완전한 복구는 보장하지 않는다.

기본 위치는 프로젝트 공통 작업 폴더 `work/recordings/match/`이다. 다른 디스크를 쓰려면 실행 프로세스에 절대경로인 `FOOTBALL_RECORD_DIR`을 설정한다. 실행기에 필요한 기존 SRT 암호·IP 설정도 그대로 필요하며 여기에 입력하거나 로그로 남기지 않는다. 디렉터리를 생성할 수 없으면 실행이 실패한다. 실행기는 시작 시와 실행 중 60초마다 저장 드라이브의 빈 공간을 확인하고 30 GiB 미만이면 실행 터미널의 표준 오류에 경고한다. 대시보드 알림은 아직 없으며 터미널을 볼 수 없거나 60초 사이 공간이 빠르게 소진되면 경고를 놓칠 수 있다. 경고는 녹화를 중지하거나 파일을 삭제하지 않는다. 영상과 개인정보의 보관·접근 권한은 별도 관리한다.

보안 수신기가 실제로 실행 중이어야 녹화된다. 기존에 실행 중인 서버는 자동 교체하거나 재시작하지 않는다. 평문 데모와 로컬 실험용 시뮬레이터는 이 실행 경로가 아니며 자동 녹화되지 않는다. 일반 RTSP 읽기 전용 확인과 달리 실제 아이폰 수신·외부 연결은 이 실험에서 시험하지 않았다. 변경된 코드가 실제로 실행되는지 기동 로그와 생성된 파일을 확인해야 한다.

MediaMTX 1.21.3 별도 loopback 인스턴스에서 로컬 H.264 테스트 영상을 SRT로 게시해 MP4 파일 1개(377,430바이트)가 생성됐고, ffprobe는 약 6.47초를 읽었다. FFmpeg 전체 디코딩 오류도 0이었다. 이 시험은 오디오·재접속·10분 경계·전원 장애·장시간·Moblin을 검증하지 않는다. 테스트 파일은 `work/record-config-smoke-20261111/recordings`에 보관했다.

참고: [MediaMTX 녹화 기능](https://mediamtx.org/docs/features/record), [설정 항목](https://mediamtx.org/docs/references/configuration-file).

## 셀룰러 송출을 위한 SRT 수신기

Windows 방화벽이 특정 실행 파일 경로를 허용할 때 실행기의 자체 복사본에는 그 규칙이 적용되지 않는다. 이 PC에서 기존 승인 규칙의 `football-coach-server/mediamtx/mediamtx.exe` 복사본을 사용하려면 명시적으로 `FOOTBALL_SRT_APPROVED_BINARY=1`을 설정한다. 기본값은 기존대로 현재 프로젝트의 `mediamtx/mediamtx.exe`다. 옵션은 다른 임의 경로를 허용하지 않으며 방화벽을 변경하거나 네트워크 접근 성공을 보장하지 않는다.

수신 프로세스를 직접 실행할 때 `FOOTBALL_SRT_PORT=8890`, `FOOTBALL_RTSP_PORT=18554`, `FOOTBALL_SRT_BIND_IP=<PC의 사설 IPv4>`를 지정한다. 기본적으로 `FOOTBALL_SRT_PUBLISHER_IP` 한 주소만 허용한다. 셀룰러 IP가 변하는 시험은 `FOOTBALL_SRT_ALLOW_ANY_PUBLISHER=1`로 발신 IP 제한만 해제할 수 있으나 SRT 암호는 필수다. 이 옵션은 누구든 연결 시도를 할 수 있게 하므로 노출 범위와 사용자 환경을 확인한다. `FOOTBALL_SRT_PASSPHRASE`에는 안전하게 전달받은 32~64자의 ASCII 비밀이 필요하며 명령줄이나 로그, Git에 남기지 않는다.

Moblin의 SRT 연결 목적지에 PC의 공개 주소와 UDP 8890을 사용하고 Stream ID를 `publish:match`로 설정한다. 앱의 SRT 암호 설정에 같은 암호를 입력한다. Moblin 버전별 화면과 실제 아이폰 암호화 호환은 미검증이며, 사설 주소·공유기 포워딩·방화벽·공인 주소는 현장 상태를 확인해야 한다. RTSP는 PC 내부 `rtsp://127.0.0.1:18554/match`에만 열리며 분석 서버의 `/api/v1/start` 입력으로 사용한다. HTTP 화면의 로그인 암호와 SRT 암호는 다르다. 녹화는 `work/recordings/match`의 10분 fMP4, 자동 삭제 없음이다.

독립 loopback 시험에서 암호화된 SRT 합성 영상이 TCP RTSP로 10프레임 디코딩되고, ffprobe가 읽는 MP4가 생성됐다. 같은 방식으로 격리 영상을 기존 분석 API 18081에 연결했을 때 `/start` 200 및 분석 시간 갱신을 확인했고 테스트 후 idle로 되돌렸다. 이 시험의 임시 파일 삭제는 Windows 파일 잠금 때문에 실패해 테스트 폴더를 보존했다. 실제 아이폰·외부망·음성·10분 경계·장시간 재연결은 확인하지 않았다.

`scripts.wait_srt_analysis`는 loopback의 `rtsp://127.0.0.1:18554/match`에서 `ffprobe`가 실제 비디오를 확인한 뒤에만 18081 분석을 시작한다. 이미 분석 중이거나 파일 모드면 현재 입력을 교체하지 않는다. 기존 인증된 수신기와 분석 서버를 별도로 켜야 하며, 수신 중지와 재연결, 전체 지연 및 스트림 장애에서 재시작은 장시간 검증되지 않았다. 통합 localhost 합성 시험에서 수신 대기 후 분석이 시작돼 9.64fps 상태를 확인하고 테스트 종료 뒤 idle로 되돌렸다. 외부 리스너는 켜지 않았다.
