# 카메라 보정 오류 수정과 실시간 처리 검증

## 결론

이전 작업에서 ByteTrack에 연결한 카메라 보정에 **상태 좌표계 오류**가 있었다. 이를 수정하고 타일·역할 분류 배치 처리, 반정밀도 추론, 불필요한 색상 변환 생략, 최신 프레임 수신·프리뷰 게시를 구현했다.

녹화 영상을 실제 시간대로 보내는 30초 시험에서 분석·프리뷰 150개를 게시했다. 디코딩 완료부터 분석까지 지연은 중앙값125ms, 95백분위153ms, 최대170ms였다. 그러나 같은 외부 경기에서 미대응 상자 감소와 동시에 ID 변경·다른 선수 연결이 증가했다. **속도·프레임 적체 개선과 추적 정확도 개선을 동일한 성공으로 취급하지 않는다. 새 후보는 운영 배포하지 않았다.**

기존 분류·정답 JSON1190개 해시가 모두 동일하다. 운영 서버·녹화·공유기·방화벽은 변경하지 않았다.

## 직접 확인한 원인

ByteTrack의 Kalman 상태는 XYAH(중심 x·y, 가로세로비 a, 높이 h)다. 이전에 연결한 설치본 `ultralytics/trackers/utils/stracks.py::multi_gmc`는 XYWH용이며 소스에도 XYAH 사용자는 별도 구현해야 한다고 명시한다. 비율 a와 픽셀 높이 h를 같은 평면의 폭·높이로 변환해 작은 회전에 상자 폭이 크게 변했다.

설치된 helper를 실제 실행한 재현:

| 원래 상자 | 회전 | 회전 후 둘러싼 상자의 올바른 폭 | 이전 구현 폭 |
|---|---:|---:|---:|
| 18×60px | 0.1° | 18.105px | 24.283px |
| 18×60px | 1° | 19.044px | 80.821px |
| 18×60px | 2° | 20.083px | 143.565px |

확대1.02배도 폭18.36px 대신18.7272px로 이중 확대됐다. 새 XYAH 경로는 중심·이동 속도만 회전하고, 균일 줌에는 높이·높이 속도와 공분산을 함께 변환한다. 가로세로비는 보존한다. 회전마다 상자를 둘러싸며 계속 키우는 대신 인물 상자를 세운 채 유지하는 보수적 근사이며, 모든 투영 변형의 정확한 복원이라는 뜻은 아니다.

추가로 최근 추적 예측과 현재 탐지의 일대일 IoU 정합성이 실제로 좋아질 때만 변환을 적용하는 옵션을 만들었다. 정답 ID는 이 검사에 사용하지 않는다. 카메라 변환 추정이 내부 검사를 통과했다는 것과 실제 tracker에 적용됐다는 것은 별도 상태다.

## 같은 영상의 전후 추적 비교

이전과 동일한 경기305·306, 각0–30·300–330·600–630초를 사용했다. 총180초이며 모든 조건을 같은5Hz 시점900프레임에서 채점했다. 학습은 하지 않았고 정답은 채점에만 사용했다. 이미 본 영상에서 개발·비교한 결과이며 독립 최종 평가나 야간 일반화 증거가 아니다.

| 조건 | ID 변경 | 같은 ID가 다른 정답 선수로 넘어감 | 정답 대응 관측 | 정답 미대응 상자 |
|---|---:|---:|---:|---:|
| 원래5fps·보정 없음 | 3271 | 2425 | 5878 | 5287 |
| 직전15fps·잘못된 GMC | 2880 | 1302 | 8811 | 10464 |
| 15fps·XYAH 형식만 수정 | 3762 | 2128 | 9947 | 10293 |
| 속도 후보10fps·XYAH·정합성 검사·FP16 | 3928 | 2400 | 8818 | 9331 |

직전 잘못된 GMC와 속도 후보를 비교하면 미대응 상자는 약10.8% 줄었지만 ID 변경은약36.4%, 다른 선수 전환은약84.3% 늘었다. 형식 오류만 수정한 조건도 정답 대응 관측은 늘지만 ID 정확도까지 개선되지는 않았다. **상자 왜곡 원인을 수정했다고 추적 문제가 전부 해결됐다고 주장할 수 없다.**

원래5fps·직전15fps·속도 후보가 모두 같은 선수를 연속 관측한 공통1143쌍의 ID 변경은242·74·155회였다. 속도 후보는 원래5fps보다 낮지만 직전 후보보다 높다. 공통 부분집합만으로 전체 성능을 대표하지 않는다.

미대응 상자에는 정답에 없는 사람과 위치가 어긋난 상자도 들어가므로 모두 오탐이라고 확정하지 않는다. ID 전환은 IoU≥0.5 대응에 기반한 진단이며 공식 HOTA/IDF1이나 모든 장면의 사람 검수가 아니다. 서로 다른 조건의 대응 관측 수가 달라 총 ID 변경만으로 판단하지 않는다.

전체 화면 평가기의 빠른 조건은10fps·FP16·카메라 특징 다운샘플4·정합성 검사다. 실제 야간 실행기의 공간 타일 배치 경로는 다음 정답 자료와 녹화 재생으로 따로 검증했다. 서로 다른 파이프라인 검증을 하나의 통합 정확도 수치처럼 합치지 않는다.

## 속도 개선과 탐지 정답 보존 검사

1. 384px 공간 타일14개를 매번 순차 호출하던 것을 배치로 전달한다. 기본 순차 옵션은 유지했다.
2. 같은 프레임의 선수별 역할 모델 호출을 하나로 묶는다. 실제 저장 모델·선수31명에서 CPU 중앙값7.62→3.99ms, 누적 분류 결과는 동일했다.
3. GPU FP16을 선택할 수 있게 했다. 설치본의 `quantize=16`을 사용한다. 모델 가중치 파일을 다시 저장하거나 학습하지 않았다.
4. GPU 결과는 타일당 한 번만 CPU로 복사하고, 작은 중복 제거 루프는 Python float로 처리한다.
5. 분석하지 않는 원본 프레임은 grab만 하고 BGR 변환을 생략할 수 있다. 원본30개 선택 프레임의 픽셀 해시가 기존 read 경로와 동일했다.
6. 프리뷰는 작업 중1개·최신 대기1개로 제한한다. 이미지와 분석 데이터를 함께 복사·교체해 서로 다른 시점이 섞이지 않게 한다.
7. 최신 입력 수신기는 대기 프레임1개만 유지한다. 입력 영상은 그대로 읽고, 분석 작업이 오래된 프레임을 계속 따라가지 않게 한다. 원본 녹화 파일을 지우거나 변경하지 않는다.

같은 3프레임의90개 탐지 상자에서 순차 FP32와 batch8 FP32의 모든 상자가 IoU0.99 이상으로 대응했다. 평균 탐지 시간은216→96ms였다. 이것은 전체 파이프라인 속도가 아니다.

기존42개 타일·정답126개 비교:

| 설정 | 정답 대응 | 미탐 | 미대응 예측 | 14타일 처리 중앙값 |
|---|---:|---:|---:|---:|
| 768 FP32 | 116 | 10 | 37 | 84.61ms |
| 768 FP16 | 116 | 10 | 37 | 71.96ms |
| 640 FP16 | 113 | 13 | 31 | 53.67ms |
| 736 FP16 | 116 | 10 | 34 | 71.35ms |

640은 미탐이3개 늘어 채택하지 않았다.736도 합계 미탐은 같지만 기존 인물1개를 놓치고 다른1개를 복구했으며 속도 이득은 미미해 채택하지 않았다. **최종 실행 후보는768을 유지한다.** 이 작은 정답 집합에서의 FP16 지표 일치가 모든 장면의 동일한 결과를 보장하지는 않는다. 후보 탐지 점수·상자 좌표에는 작은 수치 차이가 있다.

## 전체 실행기와 실시간 모사

사용자 녹화 `replay-1950-2010.mp4`로 팀 분류·미니맵·코칭·스냅샷 저장을 함께 실행했다. 출력은 모두 별도 work 디렉터리다.

- 같은 첫6초의 전체 실행 시간은 직전15fps 후보29.22초→새10fps 후보13.73초였다. 모두 초기 준비 포함이며 분석은31회로 같고 추적 갱신은91회→61회다. 순수 코드 최적화만의 속도 차이로 해석하지 않는다.
- 최종 비동기 후보, 60초 녹화: 전체 프로세스67.70초(초기 로딩 포함), 분석300회·추적599회, 준비 구간 이후 약4.994분석fps. 마지막 프리뷰의 원본 시각59.8초를 확인했다. 여유 있는15fps 운영이라고 부를 수 없다.
- 모델을 먼저 준비하고 실제 시간대로 입력하는30초 시험: 입력903프레임, 분석150회·프리뷰150개 모두 완료, 추적289회(약9.6fps).
- 디코딩 완료 이후 분석 시점까지 프레임 나이: 중앙값125.4ms·95백분위153.1ms·최대169.8ms.
- 입력 대기에서612프레임을 최신 프레임으로 교체했다. 30fps 입력을 약10fps 추적으로 처리하는 생략도 포함한다. 프리뷰 대기 교체0개, 게시 실패0개였다.
- 프로세스 전체37.33초에는 모델 준비 등이 포함된다. 입력이 시작된 이후에는30초 분량을 실제 시간대로 처리했다. CPU 회귀 테스트가 병행된 환경이었다.

이 지연은 **아이폰·셀룰러·SRT·디코딩까지 포함한 종단 지연이 아니다.** 실제 외부 송출은 이번에 시험하지 않았다. 최신 프레임을 선택해 오래된 입력의 누적은 제한하지만, 네트워크/디코더 내부 버퍼의 지연까지 없어진다는 의미도 아니다. 실제 입력에서 건너뛰는 프레임 패턴은 오프라인 고정10fps 평가와 다르므로 같은 추적 정확도를 보장하지 않는다.

## 실행 옵션과 안전한 적용 범위

기존 명령에 아래 옵션을 붙이는 실험 경로를 준비했다. 운영 명령 자체는 변경하지 않았다.

```text
--analysis-fps 5 --tracking-fps 10
--tracking-camera-motion --tracking-camera-alignment-guard --tracking-camera-downscale 4
--detector-batch-size 14 --detector-half --detector-tile-size 768
--grab-skipped-frames --async-preview
```

실시간 입력 또는 녹화 실시간 모사에는 `--latest-input`을 추가한다. 파일 입력에서는 `--realtime`도 필요하다. 이 경로는 모델 준비를 입력 연결 전에 수행하며 더미 준비 결과를 선수나 피드백으로 게시하지 않는다. 기존 raw ID 답과 다른 추적 설정·배치·정밀도·입력 생략을 결합하면 원래 ID를 그대로 연결하지 않도록 CLI가 거부한다. 분류 원본을 보존한 채 새 트랙과 원본 장면을 다시 대응해야 한다.

스레드 수 조정도 시험했지만 유의미한 개선이 없어 최종 후보에서 사용하지 않았다. 해당 옵션은 실행 프로세스에만 적용되며 시스템 전역 설정을 변경하지 않는다.

## 테스트·증거·남은 일

전체 테스트517개 통과·1개 건너뜀. XYAH 회전/줌/공분산, 카메라 정합성 보류, 타일·역할 배치 동일성, 최신 프레임 순번·EOF·시간제어·종료 오류, 프리뷰 이미지/분석 일치·최신 대기·오류 전달을 검사했다.

작업 루트의 `work/motion-speed-20261113/`:

- `xyah-gmc-rootcause.json`: 실제 설치 helper 오류 재현
- `eval-305/306`, `fast-eval-305/306`, `final-comparison.json`: 동일 영상 추적 비교
- `tile-batch-probe.json`, `tile-precision-eval.json`, `tile-736-paired-gt-differences.json`: 탐지·속도·미탐 검사
- `live-fast-10-final/summary.json`: 1분 처리량
- `live-realtime-bounded/latency-summary.json`, `execution.json`, `stdout.bin`: 실제 시간대 입력 모사 및 지연/프레임 통계
- `label-preservation.json`: 기존1190개 JSON 해시 보존

카메라 형식 오류 수정과 처리량·적체 개선은 구현했다. 남은 핵심은 잘못된 선수 연결을 줄이는 데이터 대응과 실제 운영 부하에서의 여유 확보다. 이번 후보는 그 정확도 기준을 통과하지 못했다. 기존 운영을 교체하거나 새 질문을 대량으로 만들지 않았다.

외부 모델/데이터를 새로 받지 않았고 기존 Ultralytics AGPL-3.0 조건은 유지된다.
