# 추적 주기 및 카메라 움직임 보정 비교

## 결론

추적을 15fps로 높이면서 분석·팀 투표·미니맵·코칭 출력은 기존 5fps로 유지하는 경로를 구현했다. 배경 특징으로 카메라 움직임을 보정하는 옵션도 추가했다. 기존과 같은 경기 305·306의 같은 구간에서 비교한 결과, **15fps+보정은 5fps 대비 ID 변경과 동일 ID의 다른 선수 연결을 줄였지만 미대응 상자가 크게 늘었다.** 실시간 처리량도 충분히 확인되지 않아 기본 운영 설정을 바꾸거나 서버를 재시작하지 않았다.

기존 분류·정답 JSON 1190개의 해시가 동일하다. 고주기 추적에서 raw ID가 바뀌므로 기존 장면별 raw ID 연결 답을 그대로 적용하는 조합은 CLI에서 거절한다. 답변을 삭제하지 않으며 원본 근거를 통한 재검증·학습에는 계속 사용할 수 있다.

## 공정 비교 방법

- 이전 실험과 동일한 AI Hub 경기 305(`video-02.mp4`)·306(`video-04.mp4`), 각 0–30·300–330·600–630초. 총 180초.
- 5fps/15fps 각각 보정 없음/있음 네 가지 조건. **모두 같은 5Hz 시점 900프레임에서 채점**한다. 프레임 수를 늘려 단순 오류 개수가 달라지는 문제를 피했다.
- 15Hz에서 YOLO11n(imgsz1280, conf0.1) 탐지를 한 번 수행한 뒤 같은 상자를 해당 시점의 각 tracker에 전달한다. 5Hz 조건은 중간 관측에 접근하지 않는다.
- 추적 유실 허용 시간을 동일하게 10초로 유지한다. 설치된 BYTETracker는 buffer를 갱신 횟수로 사용하므로 5Hz=50회, 15Hz=150회다.
- 학습이나 새 재연결 모델은 적용하지 않았다. 기존 ByteTrack 자체의 주기·카메라 보정만 비교한다.
- 정답은 채점에만 사용한다. 이번 실험은 이미 확인한 동일 영상의 전후 비교이며 미사용 최종 평가나 야간 일반화 증거는 아니다.
- 모든 방식이 같은 선수를 연속 두 시점에 대응시킨 공통 관측 쌍도 별도로 비교한다. 총 438쌍이며 쉬운/가시적인 부분집합일 수 있다.

## 결과

| 조건 | ID 변경 | 같은 ID가 다른 정답 선수로 넘어감 | 정답 대응 관측 | 정답 미대응 상자 | 공통 438쌍 ID 변경 |
|---|---:|---:|---:|---:|---:|
| 5fps | 3271 | 2425 | 5878 | 5287 | 66 |
| 5fps+카메라 보정 | 1969 | 1290 | 3844 | 7506 | 41 |
| 15fps | 4585 | 2654 | 11398 | 7772 | 36 |
| 15fps+카메라 보정 | 2880 | 1302 | 8811 | 10464 | 24 |

15fps+보정을 기존 5fps와 비교하면:

- 전체 ID 변경: 3271→2880, **12.0% 감소**.
- 같은 ID의 다른 선수 전환: 2425→1302, **46.3% 감소**.
- 공통 관측 쌍 ID 변경: 66→24, **63.6% 감소**. 전체 경기의 ID 정확도가 63.6% 개선됐다는 뜻은 아니다.
- 정답 대응 관측: 5878→8811, 약 49.9% 증가.
- 정답 미대응 상자: 5287→10464, 약 97.9% 증가. **탐지 오탐이 줄었다고 주장할 수 없다.**

5fps+보정의 ID 변경이 더 적지만 대응 관측도 줄었으므로 더 좋은 설정으로 선택하지 않았다. 15fps만 높이면 대응 관측이 크게 늘어 전체 ID 변경 개수도 증가한다. 공통 관측에서는 개선되지만 이를 전체 오류 감소와 혼동하지 않는다.

같은 ID의 다른 선수 전환은 한 평가 창 안에서 같은 추적 ID에 순차적으로 다른 정답 인물이 대응한 횟수다. 별도 재연결 모델이 제안한 연결 수가 아니므로 직전 보고서의 오연결 2건·3건과 직접 비교하면 안 된다. 이 지표도 IoU≥0.5 대응에 기반한 진단이며 사람이 모든 오류를 검수한 결과나 공식 HOTA/IDF1은 아니다. 미대응 상자에는 정답에 없는 인물, 위치가 어긋난 상자 등이 포함될 수 있어 전부 오탐이라고 부를 수 없다.

## 카메라 보정 구현

설치된 BYTETracker는 gmc 객체가 있어도 이미지 대신 None을 넘기면 보정을 수행하지 않는다. 새 경로는 원본 프레임을 전달한다.

이전·현재 프레임의 탐지 인물 영역을 제외하고 배경 특징을 추적한다. 왕복 광류 오차, RANSAC 내점 수·비율, 특징 분포, 회전·확대·이동 범위를 검사한다. 기준에 못 미치면 항등 변환으로 돌아가며 적용/거절 횟수를 기록한다. reset 때 카메라 객체도 새로 생성한다.

15fps에서 보정 2650회 적용·44회 거절·6회 초기화. 이것은 내부 검사를 통과한 횟수이며 카메라 변환의 실제 정확도 점수가 아니다. 경기장 미터 좌표 보정은 별도 기능으로 유지한다.

## 부작용 조사

보정을 켜면 15fps 단독보다 정답 대응 관측이 줄었다. 경기 305 첫 10초를 추가 검사해 Kalman 출력 상자 대신 현재 탐지기의 실제 대응 상자를 채점하면 다음과 같았다.

| 조건 | Kalman 상자의 정답 대응 | 실제 탐지 상자의 정답 대응 |
|---|---:|---:|
| 15fps | 637 | 673 |
| 15fps+보정 | 511 | 587 |

상자 위치 필터링의 오차가 일부 영향을 주지만 실제 탐지 상자로 바꿔도 보정 조건이 더 낮았다. 따라서 단순 좌표 출력 변경만으로 해결됐다고 보지 않는다. 카메라 변환과 추적의 데이터 대응을 함께 검증해야 한다. 이 조사 결과로 모델이나 임계값을 튜닝하지 않았고, 운영 상자 출력을 바꾸지 않았다.

## 실제 실행기 검증과 처리량

새 옵션:

```text
--analysis-fps 5 --tracking-fps 15 --tracking-camera-motion
```

현재 추적 옵션은 실험용이며 기본값은 기존 동작이다. 입력 프레임 격자에서 분석 시점이 빠지지 않도록 tracking interval이 analysis interval을 나누어야 한다. 30fps 원본에서는 각각 2프레임·6프레임이다. 처리율은 설정값과 실제 게시율을 구분해 기록한다.

사용자 녹화 6초를 같은 실행기로 별도 출력 디렉터리에 재생했다. 운영 게시 경로와 정답 저장소에는 쓰지 않았다.

- 기존: 분석 31회, 전체 프로세스 약 14.61초.
- 새 경로: 추적 91회·분석 31회, 보정 90회·초기화 1회, 전체 프로세스 약 29.22초(명령 기록과 로그 작성 시각 차이).
- 양쪽 모두 코칭 알림 1건 생성. 알림이 실제 전술적으로 옳다는 검증은 아니다.
- 초기 모델 로딩 등을 포함하므로 정상 상태 FPS로 환산하면 안 되지만, 이 시험으로 **고해상도 타일 분석 경로의 실시간 15fps 처리를 보장하지 못한다.**

다른 경기의 전체 화면 평가에서는 탐지 평균 약 19–20ms, 15fps+보정 tracker 약 32–35ms였다. 이 수치에 역할 분류·타일 탐지·게시가 모두 포함된 것은 아니다. GPU 측정 peak allocated 약131MiB는 해당 프로세스의 PyTorch 할당량이며 시스템 총 GPU 사용량이 아니다. 네 조건을 동시에 비교한 실험의 전체 벽시계 시간(약102–113초/90초 영상)을 단일 운영 경로의 속도로 해석하지 않는다.

별도 최종 1초 시험에서 추가된 실제 게시율·추적 횟수·보정 상태 기록을 확인했다. 증거는 live-smoke-final/summary.json이다.

## 남은 개선과 적용 결정

1. 카메라 변환의 품질 판정에 현재 탐지와 추적 예측의 정합성을 추가하고, 변환 오차가 커지는 구간을 확인해야 한다. 보정이 항상 이득인 것은 아니다.
2. 현재 탐지 상자와 Kalman 상자 차이 및 새 인물·관중·중복 상자를 함께 검사해야 한다. ID 변경 감소만으로 승격하지 않는다.
3. 전체 화면 평가보다 비싼 고해상도 타일 실행기를 최적화하고 충분한 길이로 처리량을 재야 한다. 실시간 스트림의 프레임 적체를 막는 최신 프레임 수신 정책도 필요하다. 현재 순차 OpenCV 경로에 고주기만 켜면 지연이 쌓일 수 있다.
4. 기존 수동 답변은 그대로 보존한다. 설정 변경으로 raw ID가 달라진 뒤에는 원본 장면 근거와 새 트랙을 대응시켜 재검증해야 한다.

운영 기본값·서버·녹화는 변경하지 않았으며 병합·배포하지 않았다. 사람에게 새 분류 질문을 추가하지 않았다. 이번 문제는 정답 부족만이 아니라 추적 주기·카메라 변환·처리량의 문제다.

## 재현·테스트·버전

```powershell
python scripts/evaluate_tracking_cadence.py VIDEO TRACK_JSON YOLO_WEIGHTS NEW_OUTPUT_DIRECTORY
python -m pytest tests/test_tracking_motion.py -q
```

증거: 작업 루트의 `work/tracking-cadence-20261113/` 아래 eval-305/306의 comparison.json·trace.json·identity-errors.json, aggregate.json, measurement-probe.json, live-smoke 및 live-smoke-baseline, label-preservation.json.

전체 테스트 486개 통과·1개 건너뜀. 이후 추가한 오래된 raw ID 연결 거절 테스트를 포함한 관련 테스트 5개도 통과했다. 평행이동 복원, 배경 특징 부족 시 보류, 인물 전체 마스크, 실제 GMC 호출, 주기·유실시간 계산을 실행 검증했다.

새 외부 모델·데이터를 다운로드하지 않았다. 기존 Ultralytics BYTETracker와 YOLO11n은 기존 AGPL-3.0 라이선스 조건을 따른다. 배경 광류 구현은 프로젝트 코드이며 OpenCV LK/RANSAC을 사용한다.
