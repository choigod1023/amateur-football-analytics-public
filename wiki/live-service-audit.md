# 라이브 코칭 서비스 심층 점검 (2026-11-16)

점검 범위: 영상 입력부터 알림이 코치에게 닿기까지. GPU를 쓰는 실행은 하지 않았고(검출기 학습이 GPU를 사용 중), 코드 읽기, 저장된 추적 파일 재생(CPU), 단위 시험, 저장된 로그와 사용자님 판정 집계로만 점검했습니다. 운영 서버 재시작, 푸시, 커밋은 하지 않았습니다.
근거 파일: `scripts/run_live_feedback.py`(306줄), `app/live_feedback.py`(178줄), `scripts/replay_live_feedback.py`, `app/main.py`(입력 정지 표시), `app/alert_review.py`, `docs/live-feedback.md`, `work/human-labels/public-own-match-review-20261111/alerts/`(gk2-h1, gk2-h2, labels), `work/live-real-1116b/run*.log`, `work/motion-speed-20261113/`, `work/tracks-ov3-20261113/h1_v3.json`, `h2_v3.json`.

## 1. 결론
**지금 상태로는 경기 현장에서 코치가 믿고 쓰는 라이브 코칭으로 운영하기 어렵습니다.** 분석 엔진 자체는 실시간으로 돌 수 있지만, 입력이 끊기면 멈추고, 알림 정확도가 확정되지 않았으며, 알림이 코치에게 전달되는 경로가 없습니다. 영상 한 경기를 재생하며 사람이 옆에서 보는 시연에는 쓸 수 있습니다.

| 항목 | 판단 | 근거 |
|---|---|---|
| 분석 속도 | 가능 | 분석기 한 번에 평균 13.7ms (아래 2절) |
| 검출 속도 | 빠듯함 (이 코드는 약 1배속) | 4분 영상 250초(위키 기록), 박스 확대를 켜면 1.47배 느림 |
| 입력 끊김 복구 | 없음 | 아래 3절 |
| 알림 정확도 | 확정 불가, 현재 판정 기준 약 72% (표본 25개) | 4절 |
| 알림 전달 | 없음 (터미널, 파일, 평가 화면, 미리보기 영상뿐) | 6절 |
| 알림이 늦는 문제 | 득점 장면 중 소수만 15초 이상 앞서 알림 | 4절 |
| 보안 | HTTP 무인증 (시제품, 공개 배포 전 인증 추가 필요) | 6절 |

## 2. 구조와 지연
경로: 영상(파일, 카메라, 스트림) → 타일 검출(384px 조각을 768로 확대) → ByteTrack → 팀 투표 → 보정으로 미터 좌표 → `LiveAnalyzer` → 알림(터미널 출력, `alerts.jsonl`, 미리보기 영상의 하단 띠, 평가 화면 `/alerts`).

**처리 시간 (측정)**
- 검출과 추적: 4분 영상을 250초에 처리 (이 코드의 스크립트, 이전 세션 측정). 박스 확대를 켜면 352초. 즉 1배속 안팎이고 여유가 거의 없습니다.
- 분석기(`LiveAnalyzer.update`): 저장된 후반 추적 5,880번 호출을 CPU로 재생해 평균 13.7ms, 99번째 백분위 121ms, 최대 198ms. 알림이 나오는 호출은 평균 69ms, 최대 175ms. 5fps 분석의 한 프레임 예산이 200ms이므로 최악의 경우 예산 거의 전부를 씁니다. 학습이 CPU도 쓰고 있는 상태에서 잰 값이라 단독으로 재면 더 빠를 수 있습니다.
- 메모리: 19.6분 재생 동안 분석기의 파이썬 메모리가 0.61MB에서 0.88MB로만 늘었습니다. 최근 24초만 보관하며(프레임 121개), 선수 길 구조는 시간 창을 넘으면 지웁니다. 다만 `placed`와 `box_history`는 초마다 1개씩 계속 쌓입니다 (한 경기 약 3,000개 수준이라 문제 없음). 모델과 GPU 메모리는 재지 않았습니다.

**알림이 늦게 나오는 구조적 이유 (코드로 확인)**
- 조건이 시간을 요구합니다: 박스 침투는 연속 2초 이상 3명, 고립은 6초, 라인 간격은 5초, 라인 하락은 10초 창, 침투는 끝난 뒤 2초 이내.
- 알림은 한 초가 끝난 뒤 그 초를 닫을 때 나옵니다. 그래서 상황이 시작되고 알림이 나오기까지 가장 빠른 경우가 박스 침투 약 3초, 그 밖에는 5~11초입니다. 처리와 전달 지연은 별도입니다.
- 이전 세션에 측정한 더 새로운 코드(별도 실험 코드, 5절)에서는 프레임이 도착해서 분석될 때까지의 지연이 30초 시험에서 중앙값 125ms, p95 153ms, 최대 170ms였습니다. 이 코드로는 측정하지 못했습니다.

**알림이 실제로 쓸모 있는 시간 안에 오는가 (재생 결과)**
저장된 추적을 재생해 득점 장면에서 득점 20초 전부터 3초 후 사이의 박스 침투 또는 침투 알림을 확인했습니다.

| 득점 장면의 결과 | 해석 |
|---|---|
| 15초 이상 전에 알림 | 코치가 대응할 수 있는 시간 |
| 2초 전에 알림 | 너무 늦음 |
| 득점 뒤에 알림 | 득점 뒤라 경고가 아님 |
| 알림 없음 | 놓침 |

- 15초 이상 앞선 경우는 득점 장면 중 소수(절반 미만)입니다. 박스 침투 알림이 분당 약 0.8회 나오므로, 20초 창에 우연히 하나가 들어갈 확률이 이미 상당합니다(우연 기준선은 계산하지 않았음, 추정).
- 이 재생은 저장된 추적(오프라인에서 앞뒤 정보로 이어 붙인 값)을 쓰므로 실제 라이브보다 유리한 조건입니다. 실제 라이브 4분(110~350초) 실행에서는 한 골 직전에 박스 안 선수가 검출되지 않아 박스 침투 알림이 나오지 않았습니다 (`work/live-real-1116b/run*.log`).

- 전반 61개/23분(분당 2.66), 후반 47개/19.1분(분당 2.47). 코치가 읽기에 많다는 기준(분당 2개)을 넘습니다.

## 5. 이 코드와 별도 실험 코드의 차이 (중요)
같은 스크립트를 고친 별도 실험 코드가 있고, 이 코드의 `run_live_feedback.py`는 306줄인데 실험 코드는 611~639줄입니다. 그쪽에는 다음 옵션이 있습니다(코드에서 확인, 실행은 하지 않았음): `--latest-input`(밀린 입력 폐기), `--motion-guard`와 `--tracking-camera-motion`(카메라 흔들림과 외형 불연속 감시), `--tracking-fps`, `--detector-batch-size`, `--detector-half`(FP16), `--async-preview`, `--publish-dir`(대시보드 공개), `--observations`, 재연결 규칙(`ReviewedReconnector`). 대부분 도움말에 "experimental"이나 "not validated"가 적혀 있습니다.
- 이전 세션의 측정(`work/motion-speed-20261113/`, 30~60초 시험): 분석 FPS 약 4.99(분석 상한 5fps), 단계별 평균 검출 74ms, 추적 11ms, 그 밖 18ms로 합계 약 104ms. 60초 영상에 전체 68초(모델 로딩 포함). 입력은 `decoded 903, delivered 291, discarded 612`로 최신 프레임만 남겼습니다. 지연 중앙값 125ms.
- 이 측정은 같은 구간 한두 개이고 모델 FP16의 정확도 검증이 따로 필요하다고 문서에 적혀 있습니다. 이 코드로 옮겼을 때 효과는 확인하지 못했습니다. 어느 쪽이 최신 운영 후보인지도 확인하지 못했습니다.

## 6. 운영 요소
**시작 절차(사람이 입력해야 하는 것)**
- 카메라 이름과 보정 파일 선택, 공격 방향(`--direction`), 팀(`--team`), 배경 보정 값 4개, 이동 값, 경기장 길이와 폭, 선택적으로 분류기. 값은 경기마다 사람이 정합니다. 공격 방향이 반대로 들어가면 모든 알림의 의미가 뒤집힙니다 (자동 확인 없음).
- 전반과 후반이 바뀌면 방향이 바뀝니다. 스크립트는 한 번 실행에 방향 하나를 씁니다. 방향을 바꾸려면 프로세스를 다시 시작해야 하고 그동안 알림이 끊깁니다. 이 경기는 카메라 자체도 중간에 바뀌므로(cam1에서 cam3) 보정 파일과 배경 보정 값도 바꿔야 합니다.
- 새 경기장이나 새 카메라 위치에는 사람이 보정 기준점을 새로 찍어야 합니다 (`research-calibration.md`에서 자동 보정은 쓸 수 없다고 정리).

**전달 경로**
- 터미널 출력, `alerts.jsonl`, 미리보기 영상의 하단 띠(`--video-out`, 마지막 8초만 표시), 평가 화면 `/alerts`(10초마다 새로 불러오는 평가용 목록이며 알림 시각이 아니라 판정 도구).
- 코치 태블릿이나 사이드라인 푸시 알림은 구현되어 있지 않습니다. 전달 지연과 읽을 수 있는 크기는 확인하지 못했습니다.
- 미리보기 영상 하단 띠는 처리 지연이 쌓이면 오래된 알림을 늦게 보여 줍니다.

**보안과 장애 시 대체**
- 평가 화면의 판정 변경에는 접속 토큰이 없고 HTTP 평문인 시제품입니다(공개 배포 전에는 인증을 추가해야 함). 알림 내용에는 개인 정보가 없지만 같은 서버가 경기 영상 화면과 라벨 저장소도 보여 줍니다.
- 장애 시 대체 동작(알림 없음 표시, 자동 재시작, 상태 표시)이 이 스크립트에는 없습니다. "알림이 없다"가 평온함인지 시스템이 멈춘 것인지 코치가 구별할 수 없습니다(입력 정지 표시는 대시보드 경로에만 있음).

## 8. 가장 먼저 고칠 것 3가지 (제안)
1. 입력 끊김 재연결과 프레임 처리 예외 처리, 입력 정지 표시 (순위 1, 2). 구현이 작고 위험이 큽니다.
2. 밀림 방지: 최신 프레임만 남기는 입력과 알림 나이 표시. 별도 실험 코드에 구현이 있으니 옮겨 오기 전에 FP16과 큐의 정확도를 이 경기로 먼저 재확인합니다 (순위 3).
3. 상태형 알림의 반복 제거와 전반 판정 후 종류별 기준 조정 (순위 7, 8). 사용자님의 `gk2-h1` 판정이 필요합니다.

## 9. 확인하지 못한 것
- GPU를 쓰는 실제 라이브 실행과 속도 재측정(학습이 GPU를 사용 중이라 하지 않음), 이 코드로 옮긴 실험 코드 옵션의 효과.
- 실제 아이폰 송출, 셀룰러 환경, 장시간(90분) 안정성, GPU와 모델의 메모리 증가, 스트림 재연결 시 동작(재연결 코드가 없는 것만 확인).
- `gk2-h1`(전반 61개)의 정확도, 알림이 코치에게 실제로 쓸모 있었는지, 알림 지연 측정(종단 간).
- 득점 외의 중요한 순간에 알림이 나오는지(재현율). 득점 장면은 작은 표본입니다.

### 동작
1. **최신 프레임 큐** (`--latest-input` / `--no-latest-input`): 스트림과 카메라는 기본 켜짐, 파일은 기본 꺼짐(켜면 파일을 자체 프레임 속도로 읽음). 읽기 스레드가 재연결 읽기를 거쳐 프레임을 계속 읽고 **가장 최근 한 장만** 남깁니다. 분석이 느려서 건너뛴 프레임은 버리고 개수를 셉니다. 분석 주기는 영상 시간 기준으로 다시 맞춥니다(밀려서 두 주기 넘게 늦으면 현재 프레임에서 다시 시작).
2. **지연 통계**: 프레임을 읽은 시각부터 그 프레임의 분석이 끝난 시각까지를 `DelayStats`(평균, p95, 최대, 최근 300프레임)로 재서 하트비트 줄에 넣습니다. 알림 줄에는 `latency_ms`(프레임을 읽은 뒤 알림을 쓰기까지)를 더했습니다(필드 추가만, 기존 필드 이름은 그대로).
3. **하트비트 줄** (`--heartbeat-seconds`, 기본 10초): `{"kind": "heartbeat", "type": "heartbeat", "polarity": "status", "stats": {"delay": ..., "camera": ..., "queue": {"decoded", "delivered", "discarded"}}}`. 입력이 끊긴 동안(최근 20초 안에 프레임이 없을 때)은 쓰지 않습니다. 그래서 벤치 화면(`app/bench_view.py`)이 하트비트가 오래 없으면 "입력 없음"으로 표시할 수 있습니다. `polarity: status`라 `/alerts` 평가 목록에는 들어가지 않습니다. `delivered`는 큐에서 꺼낸 프레임 수이고 분석한 프레임 수가 아닙니다(분석은 주기마다 한 장).
4. **카메라 이동 보정** (`--camera-compensate`, 기본 꺼짐, 보정 사진은 `--reference-image` 또는 `--store`의 `ref_token` 사진): 경기장 쪽 특징점(ORB)을 보정 사진과 맞춰 이동(dx, dy)을 구하고 중앙값(최근 5개)으로 거른 값을 `feet_to_metres`의 `shift`에 더합니다. 5초마다 측정하고, 측정이 안 되는 짧은 공백(10초 이하)은 마지막 값을 씁니다. 이동이 24픽셀(`--max-camera-shift`)을 넘거나 크기가 2% 넘게 바뀌거나, 10초 넘게 맞추지 못하면 **상태가 'moved' 또는 'unknown'이 되어 위치와 알림을 보류**하고 `camera_moved` 줄(`polarity: status`)을 한 번 씁니다. 다시 맞으면 `camera_back` 줄을 씁니다. `--reference-bg`와는 함께 쓸 수 없습니다(같은 이동을 두 번 세게 됩니다).
5. **GPU 옵션(미시험)**: `--detector-half`(FP16), `--detector-batch`(타일 묶음). 둘 다 기본 꺼짐입니다.

- 큐 시험: 프레임 5장이 쌓인 뒤 꺼내면 5번째 프레임이 오고 4장이 버려진 것으로 세어집니다. 2 ms마다 프레임이 오고 분석이 20 ms 걸리는 가짜 입력(200장)에서 버린 프레임이 100장을 넘고 지연 최대가 250 ms 미만이었습니다(큐가 없으면 같은 조건에서 100번째 프레임이 약 1.8초 기다립니다). 파일 속도 맞추기, 끊긴 스트림 재연결과 큐의 결합, 끝나는 조건도 시험했습니다.
- 카메라 이동 시험(합성 그림): (-7, +7)픽셀 이동은 1.5픽셀 오차 안에서 측정, `shift`의 부호가 `feet_to_metres`와 맞음(드리프트한 카메라의 같은 선수가 같은 미터 위치가 됨), 60픽셀 이동은 'moved', 빈 그림과 크기가 다른 그림은 'unknown', 짧은 공백은 마지막 값 유지와 긴 공백은 'unknown', 한 번의 이상한 측정이 중앙값을 흔들지 않음.
- **이 경기 실제 프레임으로 측정(CPU)**: cam1은 영상 100~1400초에서 이동이 0.1픽셀 이하. cam3(보정 사진 대비)는 1760초 (-4.0, +6.6), 1900초 (-3.8, +5.8), 2100초 (-3.1, +5.7)픽셀이다가 2145초에 (0.0, +0.2)로 돌아오고 2160~2790초는 0입니다. 측정은 프레임당 11~16 ms입니다. 이전에 사람이 입력한 이동 일정(`0:-1.8,6.8;1950:0.3,0.3`)과 **부호와 크기가 같은 방향**이고(전환 시각은 일정 1950이 5fps 가정으로 약 2130초), 측정 전환은 2140~2150초 사이입니다.
- **실제 스크립트 CPU 실행**(`--device cpu`, 후반 시작 25초, 분석 1초에 1장, 큐와 카메라 보정과 하트비트 모두 켬): 정상 종료, 하트비트 줄이 5초마다 기록, `camera: "ok"`, 큐 `decoded 973 / discarded 510 이상`, 분석 지연 평균 약 650 ms(CPU라 느림, 첫 프레임은 모델 올리기로 2.4초). 기존 경로(`--reference-bg`와 `--shift`, 큐 없음)도 같은 조건에서 정상 종료되어 호환이 유지됩니다.

### 미시험 항목
- GPU에서 FP16(`--detector-half`)과 타일 묶음(`--detector-batch`)의 속도와 결과 차이(검출기 학습이 GPU를 쓰는 동안 실행하지 않았습니다). 기본값에서는 호출 형태가 기존과 같음을 단위 시험(가짜 모델)으로만 확인했습니다.
- 실제 스트림(SRT/RTSP)과 실제 GPU 부하에서 큐의 지연 수치.
- 카메라 보정의 **미터 단위 효과**: 위 측정은 화면 픽셀의 이동이고, 보정을 켰을 때와 사람이 입력한 이동 일정을 썼을 때의 선수 위치와 알림 차이는 비교하지 않았습니다. 사람이 입력한 `--reference-bg`(cam3: `1.003087 -0.001614 -7.41 5.61`)는 이 보정 사진 대비 측정과 같은 양이 아니어서(후반 2400초 이후 측정은 0인데 그 정적 변환은 순이동이 약 (-3.3, +6.3)) 어느 쪽이 정답인지 이 작업에서는 가리지 못했습니다. 켜기 전에 같은 구간을 두 방식으로 재생해 미터 위치를 비교해야 합니다.
- 줌 변화, 롤링 셔터, 선수가 화면 대부분을 가리는 장면.

### 남은 위험
- 읽기 호출이 반환하지 않고 멈추는 경우(스트림 소켓이 죽었는데 오류가 나지 않는 경우)는 읽기 스레드가 막힙니다. 하트비트가 끊겨 벤치 화면이 "입력 없음"으로 알려 주지만 스스로 복구하지는 못합니다. 읽기 제한 시간과 스레드를 다시 만드는 복구는 아직 없습니다.
- `latency_ms`는 프레임을 읽은 시각 기준이고 카메라 센서가 찍은 시각과 네트워크 지연은 포함하지 않습니다.
- 카메라가 크게 움직이면(24픽셀 초과) 보류만 하고 새 보정을 자동으로 만들지는 않습니다. 구도 자동 선택(`CameraViewSelector`)은 아직 연결하지 않았습니다.

### 실제 라이브 시험에 필요한 조건
1. GPU가 비어 있을 때 같은 장치로 실제 SRT 송출을 받아 `--latest-input`(기본)과 FP16/묶음 옵션을 하나씩 켜 보며 하트비트의 지연(p95)과 버린 프레임 수를 기록할 것(합격 기준은 제안: 지연 p95 3초 이하).
2. 보정 사진(`ref_token`)과 같은 해상도로 송출할 것(해상도가 다르면 카메라 보정은 'unknown'이 됨).
3. 카메라 보정을 켜기 전에 위의 미터 단위 비교를 먼저 할 것.
4. 벤치 화면에서 하트비트가 10초 간격으로 도착하는지, 케이블을 뽑았을 때 "입력 없음"이 뜨고 다시 꽂으면 복구되는지 확인할 것.
