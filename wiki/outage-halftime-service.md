## 1. 무엇을 만들었나
### A. 중단 감시 (라이브 실행과 별개)
- 검토 서버 안에서 2초마다 도는 감시 스레드가 `<저장소>/alerts/<세션>/alerts.jsonl`을 봅니다. 라이브 실행 프로세스 안에서 도는 것이 아니므로 실행이 죽어도 판단합니다.
- 기준은 알림 파일의 마지막 변경 시각, 마지막 하트비트 행의 프로세스 번호(pid), 상태 행(`no_input`, `input_back`)입니다. 하트비트 행에 `pid`와 `wall`(컴퓨터 시계)을 더했습니다(`app/live_input.py`, 기존 시험 통과).
- 판정과 원인 (코치 문구는 괄호):
| 원인 | 조건 | 걸리는 시간 |
|---|---|---|
| 영상 입력 끊김 (영상 입력 끊김) | 마지막 말이 `no_input`, 또는 분석 프로그램은 살아 있는데 하트비트가 25초 넘게 없음 | 상태 행이 있으면 1초, 없으면 약 23~25초 (측정) |
| 분석 프로세스 종료 (분석 프로그램 종료) | 마지막 하트비트의 pid가 더 이상 없음 | 0.5초 (측정) |
| 분석 응답 없음 | 파일이 25초 넘게 조용한데 pid를 확인할 수 없음(예전 실행, 다른 컴퓨터) | 25초 |
| 서버 응답 없음 | 브라우저가 서버 답을 6초 넘게 못 받음 (서버가 죽으면 서버가 스스로 알릴 수 없으므로 브라우저만 압니다) | 6초 (측정) |
- 하트비트가 한 번도 없는 실행(`--heartbeat-seconds 0`)은 "정상 여부를 알 수 없음"(노랑)이고 중단으로 치지 않습니다. 3시간 넘게 변화 없는 옛 실행은 감시하지 않습니다.
- Windows에서 `os.kill(pid, 0)`은 프로세스를 끝내 버리므로 쓰지 않고 `OpenProcess`로 확인합니다.
- 기록: `<저장소>/service/outages.jsonl`(덧붙이기만). `down`(시작 = 마지막 정상 신호 시각, 알아챈 시각 따로), `cause`(원인이 바뀜: 입력 끊김 → 프로세스 종료), `up`(복구 시각, 지속 시간), `finished`(사람이 "경기 끝, 감시 종료"를 눌러 닫음). 서버를 다시 켜도 열린 중단의 시작 시각이 이어집니다(시험).
- 화면: `/watch`(상태, 멈춤 기록 표, 하프타임 칸)와, 벤치 화면 `/bench`를 포함한 두 페이지에 붙는 `web/watch-banner.js`: 큰 빨간 띠(깜빡임), 반복 경고음(소리 켜기 버튼을 한 번 눌러야 함, 브라우저 규칙), 브라우저 알림(켜기 버튼, 허용해야 함), "소리 끄기", "경기 끝, 감시 종료". 복구되면 초록 띠가 30초 보입니다("○시 ○분에 멈췄다가 ○시에 돌아왔습니다 (○분). 이 구간은 알림과 위치 기록이 없습니다").
- 바뀐 기존 파일: `app/live_input.py`(하트비트에 `pid`, `wall` 두 칸, 상태 종류 `half_switch`), `app/review_public.py`(import 1줄과 `install_service_watch(...)` 1줄), `web/bench.html`(스크립트 1줄), `scripts/run_live_feedback.py`(후반 시작 명령 확인: import 1줄, `ControlWatcher` 1줄, 프레임 사이에 명령을 확인하는 블록 8줄, 기존 동작은 명령이 없으면 그대로). 새 파일: `app/service_watch.py`, `app/service_routes.py`, `app/halftime_accumulator.py`, `app/halftime_report.py`, `app/live_control.py`. 사람 판정 저장소에는 쓰지 않습니다.

### B. 하프타임 보고서 (2026-11-18 수정: 끊긴 뒤에 다시 계산하지 않고, 라이브 중 쌓은 누적값으로 만듭니다)
- **누적**: 검토 서버의 스레드(`HalftimeService.tick`, 2초마다)가 `positions.jsonl`과 `alerts.jsonl`의 **새로 생긴 줄만**(저장한 바이트 위치부터) 읽어 분 단위 합계로 더합니다(`app/halftime_accumulator.py`). 합계는 `<저장소>/service/halftime/<세션>/accum.json`(약 35KB)에 5초 이내 간격으로 저장됩니다. 분마다: 우리 팀 모양(앞뒤 길이, 폭, 세 줄 사이 간격, 수비 줄 높이), 상대 진영 점유, 수비 줄이 비운 쪽, 두 팀 11자리의 평균 위치. 전반 전체: 자료 없는 구간, 박스 침투(3명 이상 2초), 상대 침투 허용, 알림 종류, 두 팀 평균 좌우 위치.
- 누적은 **라이브 프로세스 밖**(서버)에서 합니다. 라이브 실행 코드는 이미 있던 `--positions` 기록 외에 추가로 하는 일이 없습니다. 분석 프로세스가 죽어도 누적 파일만 읽으므로 보고서가 만들어집니다.
- 빠진 선수 채우기와 이중 검출 합치기: 첫 11명이 다 보인 초에 11자리(역할)를 만들고, 이후 보이는 선수를 가장 가까운 빈 자리에 넣습니다. 안 보인 자리는 같은 구간의 평균 위치로 그립니다. 1.5m 안의 두 추적은 한 명으로 칩니다.
- **보고서가 만들어지는 때**: ① 코치가 "전반 끝" 버튼, ② **입력이 끊기는 순간** 실행이 전반 길이의 75% 이상 진행된 상태이면 즉시 **초안**을 자동 생성(화면 띠가 "영상이 끊겨서 하프타임 보고서를 자동으로 만들었습니다. 전반이 끝난 것이 맞습니까?"를 묻고, "맞음"이면 확정, "아님"이면 삭제하며 같은 중단에는 다시 만들지 않음), ③ 위치 기록이 1분 넘게 끊긴 구간이 전반 끝 무렵이면 제안(사람이 확인). 전반 길이 기본값 45분, `<저장소>/service/config.json`의 `{"half_minutes": n}`으로 바꿉니다. 이 경기 영상 편집본의 전반은 약 24분입니다.
- **형식(코치용)**: 한 줄 요약 문장들(어느 진영에 오래 있었나, 수비 줄 높낮이, 박스 침투와 침투 허용 장면 횟수), "팀 모양" 그림(양 팀 11명, 전반 초반/중반/후반 세 장, 우리 팀 파란색과 상대 붉은 테두리), "눈에 띈 점"(말로만: "수비 줄과 미드필드 줄 사이가 너무 벌어졌습니다 (가끔, 특히 전반 중반)", 옆으로 좁게 섬, 위아래로 늘어짐, 비운 쪽), 장면 시각 목록, 알림 횟수, "이 구간 자료 없음", 후반 확인(공격 방향 + 팀 색 재확인 + 눈에 띈 점 두 개). 검출 개수, 미터 수치, 방법 설명은 넣지 않았습니다(시험으로 확인). 말의 기준값(예: 줄 사이 18m 이상을 "벌어짐")은 코드 상단 상수이며 한 경기 관찰에서 정한 첫 값입니다(근거 없음, 조정 대상). 출력은 웹 페이지(`/halftime?session=이름`)만 만들었고 PDF는 만들지 않았습니다.
- 라인업, 포지션 카드, 골 장면 사진은 만들지 않았습니다(선수 이름 연결과 영상 장면이 라이브에서 없음).

### C. 후반 시작 버튼 (2026-11-18 추가)
- 화면 오른쪽 아래 "후반 시작": 눌렀을 때 확인 창 "후반으로 넘어갑니다. B팀이 화면 오른쪽으로 공격합니다. 맞습니까?"를 한 번 거칩니다.
- 하는 일: ① 서버가 전반 합계를 보존하고 후반 합계를 새로 시작하며(`halves` 2, 반대 방향) 라이브 실행에 명령을 보냅니다(`<세션>/control.jsonl`). ② 라이브 실행(`scripts/run_live_feedback.py`, 프레임 사이에 파일 크기만 확인)이 공격 방향을 바꾸고 `LiveAnalyzer`를 새로 만들어 보유 위치와 반복 알림 억제 시간을 비우고, `positions.jsonl`에 `{"type":"half"}` 줄과 알림 파일에 `half_switch` 상태 행(벤치 화면에 "후반 전환"으로 보임)을 씁니다. ③ 화면에 "팀 색 재확인" 띠가 "확인했음"을 누를 때까지 남습니다. ④ 후반 합계로 `/api/v1/halftime/report?session=이름&half=2`(후반 중간 보고서)를 언제든 만들 수 있습니다.
- 라이브 실행을 다시 시작해도 파일에 이미 있던 명령은 다시 실행하지 않습니다.

### 합성 장애 (복사한 코드 + 임시 저장소 + 포트 18443, 운영 서버 8443은 건드리지 않음)

|---|---|---|---|
| 프로세스는 살아 있고 영상이 멈춤(하트비트만 끊김) | 23.3초 | 영상 입력 끊김 | 파일이 다시 바뀐 뒤 2.5초 |

| 프로세스 강제 종료 | 0.5초 | 분석 프로그램 종료 | (종료 처리로 닫음) |

### 하프타임 보고서: 25분 넘게 재생한 뒤 입력을 끊어 잰 시간 (2026-11-18)
저장된 전반 추적(`work/tracks-ov3-20261113/h1_v3.json`, 24분 + 앞 5분을 한 번 더 = **28분 36초 분량**)의 초당 위치를 30배속으로 가짜 라이브 실행이 쓰게 하고(57초 동안 1,716줄), 같은 시간에 서버가 누적하게 했습니다. 서버는 복사한 코드와 임시 저장소(포트 18444)이고 운영 서버는 건드리지 않았습니다. 전반 길이는 25분으로 설정했습니다.
| 항목 | 측정값 |
|---|---|
| 입력을 끊은 순간(분석 프로세스 강제 종료)부터 보고서가 화면에 준비될 때까지 | **2.4초** (감지 0.5초 + 서버 스레드 주기 2초가 대부분, 보고서 계산 자체는 1ms) |
| 보고서 페이지 데이터 요청 | 36ms |
| 끊긴 순간 누적이 따라와 있었나 | 1,716초 중 1,716초(30배속 쓰기에도 밀리지 않음) |
| 누적 비용 | 초당 위치 1줄에 **1.2ms** (CPU, 24분 파일 1,236줄을 1.45초에 읽음), 합계 파일 35KB |
| 합격 기준(10초 이내) | **통과** |
- **라이브 알림 처리 속도 영향**: `LiveAnalyzer.update`를 저장된 전반 7,080프레임에 돌려 한 번 부르는 평균 시간이 혼자 1.0ms(세 번 0.95, 1.07, 1.04)였고, 서버가 다른 프로세스에서 28분 파일을 계속 반복해서 누적하는 동안(실제 라이브의 약 30배 부하) 1.1ms(1.12, 1.09, 1.15)였습니다. p95는 5.5~6.0ms 대 6.1~6.4ms. 차이는 0.1ms 안팎으로 측정 잡음과 구분하기 어렵고(CPU 16코어 컴퓨터), 5fps 한 프레임 예산 200ms에 비하면 무시할 수준입니다. 누적 코드는 라이브 프로세스 안에서 돌지 않습니다. **GPU 검출과 같은 컴퓨터에서 돌 때의 경쟁은 측정하지 못했습니다.**
- 이 시험은 저장된 추적을 초당 1줄로 줄인 위치이고 실제 라이브 추적(과거만 보는 추적, 보이는 선수 수가 더 적을 수 있음)이 아닙니다. 전반 앞 5분을 한 번 더 이은 구간이 있어 내용(박스 침투 18번 등)은 실제 경기 수치가 아닙니다.

#### 실제 전반 자료로 만든 보고서 예 (앞 24분, 가운데 3분은 일부러 비움)
- "전반에는 우리 팀이 상대 진영에서 더 오래 머물렀습니다. 수비 줄은 가운데쯤에 서 있었습니다. 상대 박스 안에 우리 선수가 여럿 들어간 장면이 14번, 상대가 우리 수비 줄 뒤로 뛰어든 장면이 1번 있었습니다. 영상이 끊긴 구간이 1곳 있어 그 시간은 요약에 들어 있지 않습니다."
- 눈에 띈 점: "수비 줄과 미드필드 줄 사이가 너무 벌어졌습니다 (가끔, 특히 전반 중반). 팀이 옆으로 좁게 섰습니다. 수비 줄이 가운데로 모여 양쪽 옆을 자주 비웠습니다." 이는 이전 설계 문서의 값(수비가 가운데로 모임, 왼쪽 46%와 오른쪽 49% 비움)과 같은 방향입니다. 침투 허용 1번은 1초 자료의 한계일 수 있습니다(5fps 자료와 비교하지 못함).
- 그림: 전반 초반, 중반, 후반 세 장 모두 양 팀 11명이 그려졌습니다(브라우저 화면 확인).

## 3. 못 한 것과 한계
- **실제 태블릿과 실제 경기에서 확인하지 못했습니다.** 라이브 실행(`run_live_feedback.py`)을 실제 영상으로 돌려 보지도 않았습니다(가짜 실행으로 대체). 후반 시작 명령은 실제 실행(저장 영상, CPU)에서 시험했습니다(6절). 실제 경기와 태블릿은 아직입니다. `--positions` 기록이 실제 라이브에서 하프타임까지 제대로 쌓이는지, 라이브 추적으로 만든 요약이 저장된 추적과 같은 품질인지는 모릅니다(위키 설계 문서의 미확인 항목 그대로).
- 서버와 라이브 실행이 **같은 컴퓨터**일 때만 프로세스 종료를 즉시 알 수 있습니다. 다른 컴퓨터면 "분석 응답 없음"(25초)으로만 보입니다.
- 감시가 검토 서버 안에서 돕니다. 서버가 죽으면 서버 쪽 기록도 멈추고 브라우저 띠만 남습니다(서버가 다시 켜지면 열린 중단 기록의 시작이 이어지나, 서버가 죽어 있던 시간 자체는 기록되지 않음). 서버 밖의 독립 감시(별도 프로세스, 또 다른 컴퓨터)는 하지 않았습니다.
- 정상 종료(경기 끝이나 영상 파일 끝)도 "분석 프로그램 종료"로 뜹니다. 사람이 "경기 끝, 감시 종료"를 누르면 닫힙니다.
- 알림 소리는 브라우저가 막을 수 있고(소리 켜기 버튼 필요), 브라우저 알림은 보안 연결(https)이나 localhost에서만 되는 브라우저가 많습니다(추정, 실제 태블릿에서 확인 필요). 화면이 꺼지거나 다른 앱이 앞에 있는 태블릿은 소리가 안 날 수 있습니다.
- 접근 제어가 없는 시제품입니다(같은 무선망 전제). 쓰기 경로(소리 끄기, 종료 처리, 전반 끝)가 있으므로 공개 배포 전에는 인증을 추가해야 합니다. 판정 데이터는 건드리지 않습니다.
- 전반 끝 제안 규칙의 값(1분, 75%, 45분)은 근거 있는 값이 아니라 첫 제안입니다. 후반 종료와 연장, 라이브 실행을 다시 시작해 같은 위치 파일에 덧붙인 경우(시간이 되돌아가는 줄은 무시)는 다루지 않습니다.
- 알림 문구는 코치 대상으로 풀어 썼지만, 사용자님 검토를 받은 문구는 아닙니다.

## 4. 외부 알림 채널 선택지 (만들지 않았습니다, 사용자님이 고르기 위한 설계안)
지금은 웹 페이지만 씁니다. 화면이 꺼진 태블릿이나 벤치 밖의 사람에게 알리려면 외부 채널이 필요할 수 있습니다. 모두 **계정, 연락처, 외부 서버 전달**이 생기는 점에서 사용자님 승인이 먼저입니다.
| 선택지 | 장점 | 단점과 개인정보 |
|---|---|---|
| 같은 망의 두 번째 화면(휴대폰 브라우저로 `/watch` 열기) | 계정 없음, 외부 전달 없음, 지금 바로 됨 | 화면을 켜 두고 소리를 한 번 켜야 함. 망이 끊기면 같이 끊김 |

| 메신저 봇 | 푸시가 확실하고 그룹에 보낼 수 있음 | 봇 토큰과 계정 필요, 메시지가 외부 회사 서버를 지남 |

| 이메일 | 흔함 | 늦게 보기 쉬워 즉시 알림에 약함, 주소 등록 |

- 권고(추정): 먼저 현재 웹 방식을 현장에서 시험하고(실제 태블릿에서 소리가 나는지), 부족하면 "같은 망의 두 번째 화면"을, 그다음에 ntfy 자체 서버를 검토합니다. 내용에는 경기 정보가 들어가므로 외부 전달은 중단 사실(예: "분석 중단")만 보내도록 줄이는 것이 안전합니다.
- 어느 채널이든 구현은 `app/service_watch.py`의 `_begin`, `_end`(중단 시작과 복구 지점)에 한 함수를 끼우는 것으로 끝나도록 만들었습니다(아직 그 연결 지점은 없음).
