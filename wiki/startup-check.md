# 경기 전 시작 점검 도구

작성: 2026-11-16. 근거: `scripts/startup_check.py`, `tests/test_startup_check.py`, 설계 `wiki/live-startup-and-halftime.md`. 시험 결과 파일은 `work/startup-test/<이름>/startup_report.json`과 `startup_teams.jpg`.
표시: **측정**은 이 경기 영상으로 직접 돌린 값, **제안**은 근거가 약한 임시 기준입니다.

## 무엇을 하나
입력(영상 파일 또는 스트림)에서 처음 N초(기본 20초)를 읽고 다섯 가지를 점검해서 통과, 주의, 실패로 알려 줍니다. 점검 기준(한계값)은 모두 제안값이고, 팀 색과 공격 방향은 **항상 사람이 확인해야 하는 제안**입니다. 스트림 주소는 화면과 결과 파일에 나오지 않습니다(파일은 파일 이름만 나옵니다).
1. 입력: 해상도, 프레임 속도, 프레임 사이 간격의 불규칙성, 읽기 실패 횟수
2. 사람 검출: 초마다 한 프레임을 타일 검출로 돌려, 보정으로 경기장 안에 들어온 사람 수의 중앙값(보정이 없으면 검출된 전체, 관중석으로 보이는 큰 상자와 낮은 상자는 제외)
3. 팀 색: 실시간 실행과 같은 색 규칙(형광 비율 0.10 이상이면 형광, 어두운 비율 0.30 이상이면 어두운 옷). 두 무리의 대표 사진(키 40픽셀 이상, 가장 큰 것 위주, 서로 다른 초에서 4장씩)을 `startup_teams.jpg`로 저장해서 코치가 "우리 팀은 어느 쪽인가"를 한 번 확인합니다.
4. 공격 방향: 킥오프 구간(`--kickoff`)의 처음 10초에서 두 무리의 평균 x 위치(미터)를 비교합니다. 우리 팀 평균이 더 +x 쪽이면 우리 팀이 -x(화면 왼쪽)로 공격한다고 제안합니다. 평균 차이가 5m보다 작거나, 한 무리가 프레임에서 4명 미만이면 제안하지 않습니다.
5. 보정: 파일, 해당 카메라 항목, 맞춘 오차(m), 기준 사진 유무, 현재 화면이 기준 사진에서 움직인 정도(위상 상관, 화면 너비 대비 비율)

## 사용법
```bash
python scripts/startup_check.py <영상 또는 스트림> <calibrations.json> <cam1|cam2|cam3> \
  --start 64 --seconds 20 --kickoff --reference-bg 1.000657 0.000035 -0.67 -0.47 --out startup_out
```
- `--focus-colour dark`가 기본입니다(우리 팀 B는 어두운 옷). 우리 팀이 형광이면 `bright`.
- `--tile-camera`는 cam2처럼 타일 모양이 없는 카메라에 씁니다(기본은 cam2일 때 cam3 모양).
- 종합 판정은 가장 나쁜 항목입니다. 기준 사진 위치는 `<저장소>/pending/<ref_token>.jpg`입니다(보정 파일의 두 단계 위 폴더).
- 이 도구는 기존 파일을 수정하지 않는 새 스크립트이고, 라이브 실행(`run_live_feedback.py`)에 연결하지 않았습니다.

| 33:20 경기 중, cam3 | 통과 | 24명 | 160 / 122 / 219 | 킥오프 아님: 제안 안 함 | 6.3px (0.33%) | 주의 |
- 1:04 킥오프의 방향 제안(-1)은 이전 분석(`live-startup-and-halftime.md`)과 사용자님이 알려 주신 방향과 같습니다. 한 경기 한 지점의 결과이고, 후반 킥오프는 이 시험에서 확인하지 못했습니다.
- 25:00 구간은 카메라가 24:44에 바뀐 직후여서 cam3 보정 기준 사진과 113px 어긋났고, 도구가 "다시 보정이 필요할 수 있습니다"로 실패 처리했습니다. 이 구간은 cam2일 가능성이 큽니다(기록상 후반 cam3 구간은 영상 약 29:00부터, 추정). 그래서 방향도 제안하지 못했습니다. 틀린 보정을 쓰면 위치와 방향이 틀리므로 이 실패는 의도한 동작입니다.
- 형광 상자는 대부분 확실히 잡히지만 어두운 상자는 구간마다 편차가 큽니다(48~122개). 색 규칙으로 가려지지 않는 상자가 54~62%인 구간은 "주의"가 나옵니다(제안 기준 50%).
- 전체 pytest 415개 통과, 1개 건너뜀(이 도구의 새 시험 12개 포함, 2026-11-16 시점).

## 한계
- **프레임 속도 경고는 이 영상에서 거짓 경고**입니다. 이 파일은 구간마다 프레임 속도가 다릅니다(cam1 구간 약 30fps, cam3 구간 약 60fps, 보고된 평균 44.7fps). 입력 점검이 보고값보다 느리다고 "주의"를 냅니다. 실제 스트림에서는 의미가 있지만 가변 프레임 파일에는 맞지 않습니다.
- 스트림 입력은 이 시험에서 돌리지 않았습니다(파일만). 스트림에서는 시각을 실제 시계로 재고, 읽기 실패 5번이면 멈춥니다. 확인 못 함.
- 형광색 규칙은 작고 먼 선수에 약합니다(설계 문서 측정: 키 30픽셀 미만의 형광 상자 중 43%만 판정). 그래서 대표 사진은 키 40픽셀 이상만 씁니다.
- 공격 방향은 킥오프 구간에서만 의미가 있습니다. 킥오프 시각은 사람이 `--start`와 `--kickoff`로 알려 줘야 하며 자동으로 찾지 않습니다.
- 카메라 이동 점검은 위상 상관 한 번의 값이고, 기존 `CameraMotionGuard`(ORB 특징점)는 쓰지 않았습니다. 기준 사진이 없는 보정에서는 이동을 알 수 없습니다.
- 합격 기준 수치(사람 14명 이상, 간격 0.5초와 1.5초, 이동 0.5%와 1.5% 등)는 검증하지 않은 제안값입니다.
