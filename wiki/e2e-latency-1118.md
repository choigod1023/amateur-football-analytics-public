# 종단 지연(R5) 측정: 사건에서 벤치 화면까지 (2026-11-18)

근거: `wiki/live-operations-research.md` R5와 9절(제안 합격 기준), `wiki/live-service-audit.md`, `wiki/bench-screen.md`, `wiki/srt-degradation-test-1118.md`. 도구: `scripts/e2e_latency.py`(새 파일, 기존 파일은 고치지 않음). 결과: `work/e2e-latency-20261118/full.json`(요약), `full/<조건>/frames.json`(분석한 프레임별 단계 시간), `events.json`(알림별 시간), `run.log`. 이 위키가 처음으로 잰 종단 지연이다.

## 측정 방법
- 같은 컴퓨터 안의 루프백 시험이다(밖으로 나가는 것 없음). 운영 서버(포트 8443)와 운영 중계기는 건드리지 않았다. 임시 MediaMTX와 임시 벤치 서버를 따로 열었다.
- 영상: 우리 경기 후반 약 35:00부터의 30fps 일정 간격 구간 파일(`srt-degradation-20261118/e2e2_clean_segment.mp4`, 앞 시험과 같은 파일), 1920x1080, 조건마다 앞 240초(7,200프레임).
- 시계 마커: 도구가 모든 프레임 왼쪽 위에 프레임 번호를 흑백 블록 19칸(동기 2, 번호 16비트, 검사 1)과 글자로 박는다. 받는 쪽이 블록을 읽어 어느 프레임인지 안다. 번호를 못 읽은 프레임은 7개 조건 모두 0개였다.
- 경로: 도구가 프레임을 30fps 실시간으로 ffmpeg(x264 zerolatency, 4000kbps, 조건에 따라 2000)에 넘긴다(**이 순간이 "사건 시각"**) → SRT 송출 → UDP 중계기(손실, 지연, 흔들림) → MediaMTX(SRT 수신, RTSP 중계) → 실제 `scripts/run_live_feedback.py`(RTSP/TCP로 읽음, 최신 프레임 큐 켜짐, 검출기 `ft_n2`, 팀 분류 모델, cam3, 팀 B, 하트비트 2초) → `alerts.jsonl` → 임시 검토 서버의 `GET /api/v1/bench`.
  - OpenCV에 들어 있는 FFmpeg는 SRT를 열지 못해서(주소를 열면 바로 실패) 실제 운영처럼 MediaMTX를 거쳐 RTSP로 읽었다.
- 분석 프로세스는 고치지 않았다. 도구가 같은 프로세스 안에서 네 곳(프레임 읽기, 타일 검출, `LiveAnalyzer.update`, 알림 쓰기 전후)을 감싸서 시각을 적고 마커를 읽는다. 시각은 모두 같은 컴퓨터의 벽시계(`time.time()`)다.
- 사건 표본: 영상 15초부터 8초마다 시험 신호 알림 1개를 도구가 분석기 쪽에서 넣는다(실제 알림은 조건이 3~11초 걸려 드물다). 이 신호는 실제 알림과 같은 쓰기 경로(`alerts.jsonl`)를 지난다. 신호는 그 프레임을 분석하는 순간 만들어지므로 **알림 조건에 걸리는 시간은 0**이다. 실제 알림(박스 공격, 수비 라인 하락, 침투)도 같은 방식(알림을 낸 프레임 기준)으로 따로 쟀다.
- 전달: 알림 파일은 10ms마다, 벤치 API는 100ms마다 읽어 그 줄이 처음 보인 시각을 적었다. 벤치 화면(`web/bench.js`)은 같은 주소를 1초마다 읽으므로, 화면에 나오는 시각은 "API 시각 + 다음 읽기까지의 기다림(0~1초)"로 계산했다(읽기 시작 위상 10가지로 모의, 실제 브라우저와 태블릿은 쓰지 않음).
- 조건(7개, 조건당 1번): SRT 지연 시간 120, 200, 500ms, 200ms에 OpenCV 낮은 지연 옵션, 휴대폰망 비슷한 조건(2000kbps, SRT 500ms, 손실 2%, 중계기 지연 60±40ms), 손실 10%(SRT 200ms), SRT 1500ms에 손실 5%.

## 합격 기준과의 비교
위키 R5의 지연 예산(제안)과 9절 2단계 기준(제안)에 대면 다음과 같다.
| 항목 | 예산 또는 기준 (제안) | 이번 측정 |
|---|---|---|
| 송출과 수신 | 1~2초 | 0.7~1.3초(손실과 중계기 지연 조건 포함), SRT 1500ms는 2.2초로 예산을 조금 넘음 |
| 디코딩, 검출, 추적 | 약 0.2초(앞서 잰 104ms) | 검출 0.17~0.24초, 추적 등 0.01초. 디코딩은 송출 구간에 포함. 앞의 104ms보다 길었는데 이유는 확인하지 못했다(이번 검출은 ft_n2와 타일 검출이다. 시작 전 GPU는 비어 있었지만 시험 중에 다른 프로세스가 GPU를 썼는지는 기록하지 않았다) |
| 분석기 | 0.02초 | 0.00~0.01초 |
| 전달(파일, API) | 0.5초 | 0.06초 이하. 화면 읽기 주기 때문에 화면에는 평균 약 0.5초(최대 1초) 더해짐 |
| **알림 조건 시간을 뺀 종단 지연** | (중앙값 8초, p95 15초 안에 포함되어야 함) | **API까지 중앙값 1.0~1.6초(SRT 1500ms는 2.4초), p95 1.1~1.6초(2.5초). 화면까지 중앙값 1.5~2.0초(2.9초), p95 2.0~2.5초(3.4초)** |
- 판정: **알림 조건 시간을 뺀 처리 경로만 보면 기준을 크게 만족한다.** 가장 느린 조건에서도 화면까지 p95 3.4초라 15초 기준의 약 4분의 1이다.
- **알림 조건 시간은 이 측정에 들어 있지 않다.** `coach-operating-guide.md`에 따르면 사건이 시작되고 알림이 나오기까지 박스 침투는 최소 3초(2초 넘게 머묾 조건), 고립은 6초, 라인 간격은 5초, 수비 라인 하락은 10초 안의 변화다(5~11초). 사건이 아니라 "조건이 시작된 순간"부터 세면 처리 경로 약 1.5~3.4초에 조건 시간이 더해진다. 수비 라인 하락처럼 조건이 10~11초인 알림은 처리 경로만 합쳐도 12~14.5초라 **중앙값 8초 기준을 알림 규칙 때문에 넘는다(처리 때문이 아님).** 중앙값을 알림 종류별 규칙 시간으로 따로 잰 것은 아니다. 알림 종류별 조건 시간은 위키 문서의 값을 읽었을 뿐 이번에 재지 않았다.
- 사건 시각을 사람이 정한 "진짜 사건"(예: 득점)으로 잡은 측정은 하지 않았다. 사람 판정과 지연을 연결하지 못했다.

## 알아낸 것
1. 지연의 대부분은 **SRT 지연 시간 설정**이다. 지연 설정을 늘릴수록 같은 크기로 늘었다(손실 복구에는 유리하나 알림이 늦어진다). 앞의 열화 시험(`srt-degradation-test-1118.md`)에서 지연 설정이 검출 품질에는 영향이 없었으므로, 손실이 없는 망에서는 120~200ms가 지연상 유리하다.
2. 검출 0.2초, 추적 0.01초, 분석기 0.00초로 분석 쪽은 처리 시간이 문제가 아니다. 5fps 분석(한 프레임 0.2초)을 실시간으로 따라갔고(조건당 7,123~7,166프레임 읽기 중 921~1,173프레임 분석, 큐에서 대부분 최신 프레임을 가져감) 분석 순서 기다림은 0.04초 이하였다.
3. 시작 직후 첫 분석 프레임은 느리다(7개 조건 모두 프레임 번호 30 또는 60에서 합계 3.5~4.8초, 검출 2.2~3.3초). 모델 준비 때문이며 조건당 1프레임뿐이고 이후 최대 합계는 모두 정상 범위였다. 시작 점검에서 한 프레임을 미리 돌려 두면 사라질 것이다(확인하지 않음).
4. 벤치 화면의 1초 읽기 주기가 화면 쪽 지연에 평균 약 0.5초를 더한다. 이 값은 모의 계산이고 실제 브라우저에서 재지 않았다.
5. 중계기 손실이 10%여도 지연이 0.1초 정도만 늘었다. 마커를 못 읽은 프레임은 0개라 화면 깨짐이 마커를 망가뜨린 경우는 없었다.

## 한계 (측정하지 못한 것)
- **휴대폰 카메라 촬영, 휴대폰 인코더, 실제 셀룰러망과 공유기는 포함하지 않았다.** 사건 시각은 이 도구가 프레임을 인코더에 넘긴 순간이다. 실제 휴대폰은 카메라 노출과 하드웨어 인코딩에서 보통 더 길다(이번에 재지 못했고 수치도 알지 못한다).
- 중계기는 무작위 손실과 고정 지연만 만든다. 연속 끊김, 대역폭 급감, 왕복 시간 100ms 이상은 시험하지 않았다. 그런 조건에서는 SRT가 복구하지 못하거나 지연이 크게 늘 수 있다.
- 조건당 한 번 240초(분석 프레임 921~1,173개, 시험 신호 28~29개)다. 95번째 백분위수는 알림 표본 28~29개로는 거칠다. 조건끼리 0.1초 안쪽 차이는 의미를 두지 않는다. 프레임 표본 기준 p95는 더 믿을 만하지만 알림 쪽 표본은 아니다.
- 벤치 화면 시각은 API 시각에 읽기 주기를 더한 모의값이다. 실제 태블릿, 브라우저 그리기 시간, 와이파이 전달은 재지 않았다.
- 입력은 앞 시험과 같은 우리 경기 구간 하나다. 검출기와 팀 분류 모델은 이 경기를 학습에 쓴 것이라 알림이 맞는지는 이 시험의 대상이 아니다.
- 시험 신호는 분석기 쪽에서 넣은 가짜 알림이다. 알림 쓰기와 API 경로는 실제와 같지만, 알림 문구 생성, 그림 저장(침투 알림의 `alerts_xxxx.jpg` 쓰기, 실제 침투 알림은 실제 알림 표본에 들어 있음)에 걸리는 시간은 시험 신호에는 없다.
- 지연이 10초를 넘기는 상황(분석이 밀리는 경우)은 만들지 않았다. 폐기 규칙("지연 중" 표시, 오래된 알림 폐기)을 동작시키는 시험은 하지 않았다.
- 이 측정 도중 컴퓨터가 한 번 꺼져서 본 측정이 중단되었고(5개 조건 완료 후 6번째 조건 도중), 끝난 5개 조건은 유지하고 나머지 2개를 다시 돌렸다(결과 파일 `full.before_resume.json`이 중단 시점의 복사본). 재개 때 GPU는 비어 있었다(사용 약 180MiB, 0%). 시험 중 다른 프로세스의 GPU 사용 여부는 시작 전 확인만 했다.

## 다음에 할 수 있는 것
- 휴대폰으로 시계를 찍어 송출한 영상(화면에 밀리초 시계를 띄운 컴퓨터 화면을 휴대폰으로 찍음)으로 카메라와 휴대폰 인코더를 포함한 지연을 재는 것. 이 도구의 분석 이후 단계는 그대로 쓸 수 있다.
- 실제 태블릿 브라우저에서 화면에 나타나는 순간을 재는 것(화면에 지연 표시를 넣으면 바로 읽을 수 있음).
- 지연이 예산을 넘을 때 "지연 중" 표시와 알림 폐기를 넣고 모의 지연으로 시험하는 것.
- 알림 종류별로 조건이 시작된 시각을 로그에 남겨 알림 조건 시간을 실제로 재는 것.
